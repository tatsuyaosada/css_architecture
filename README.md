### CSSの設計についての前説

 - プログラミング言語を用いてのシステム開発においては、特に大規模なものであればある程、コードをどう言った構造で組み立てるか、どの機能をどのモジュールやクラスに持たせるか、またどうやってそれを纏めるか等々、システム全体を構築するための設計と言う工程が欠かせないものになっている。一方で、マークアップ言語であるHTMLや宣言型のプレゼンテーション言語のCSSについては、コーディングルールや命名規則等はチーム単位等で定められる事が多いものの、スコープが存在しない等の仕様レベルの理由から"設計"と言う工程は今まで（と言っても10数年前レベルの話にはなるが）あまり意識されてこなかった。

- ただ、特にCSSはウェブサイトやウェブアプリを中長期的に運用していく上で、その期間に比例してコンテンツの追加やデザインの修正等、コードの煩雑化等、肥大化は昔から避けられない課題となっており、ここ数年で漸くCSSにおいても実際にコードを記述する前に"設計"と言う工程が強く意識されるようになってきた。今回の講座では主にそのCSSの設計について

  - **[OOCSS(Object Oriented CSS)](http://oocss.org/)**
  - **[SMACSS](http://smacss.com/ja)**
  - **[BEM](http://getbem.com/)**
 
 と言う設計手法をベースに紹介する。但し、CSSは言語仕様上、プログラミング言語の様なスコープ、カプセル化と言った概念が存在しないため、いわゆるシステム開発等の設計とは(概念的に流用されている部分もあるが)基本的に異なってくる事、また当然ではあるがこれらの設計手法は所謂「**銀の弾丸**」と言えるものでは到底無い。具体的に言えば、何かしらの変化に対して、全く手を入れる事がないCSSと言うのは仕様上ほぼ無理と考えて貰って良い。今回の設計手法はどれも、**変更や修正があった際に、極力手を入れ易い**と言うメンテナンスブルな思想がベースとなっている。

### 優れたCSSとは
 1. **コードからその動作が予測し易い**
    - CSSは言語仕様上、とある単一のルールセットに対し、他のルールセットが影響する事がある。単一のルールセットが極力他のルールセットに影響されず、また拡張した際にも、他のルールセットに影響を及ぼす事が無い様に設計する事が望ましい。
 2. **再利用し易い(コンポーネント指向)**
    - コピーアンドペーストでコードが肥大化する事が悪影響を及ぼす事については議論の余地はない。実装するUIに対し、同じ構造のものに対しては一つ、あるいは複数のルールセットを機能別に分割し、対象となるUIに対して使い回し出来る事が好ましい。やや抽象的な説明になってしまっているが、これについては後述するOOCSSで具体例を含めて再度解説する。
   
 3. **保守が容易である**
    - 新たなルールセットを追加する際、他のルールセットに対する副作用が生じず、既存のルールセットのリファクタリングが必要のない設計をする。
 4. **拡張性に優れている**
    - 拡張性と言うのは、実際に新たにコードを書き加えると言ったミクロな話ではない。対象となるCSSコードの設計が他の開発者にとって管理、メンテナンスし易くすべきである、と言う事である。
    
### 破綻しないCSSではなく、修正し易いCSSを意識する
 - 言語仕様上、CSSはスコープ（使用する範囲の限定化）の機能を持たず、定義したルールセットは全てグローバル（カスケードする事により容易に上書きが可能）である。そのため、完全に破綻しないコードと言うのは正直なところ現実的ではない。そのため、破綻しない（壊れない）設計ではなく、何かしら想定外の動作をした際に、修正し易い設計をする、と言うのが基本的な設計思想になる。
 
### 詳細度について

#### 詳細度とは
 - HTMLの要素に対して適用されるスタイルが重複した際に、どのルールセットを適応させるか優先順位を定めたもの。セレクタの指定が具体的であればある程優先順位が高い。例えばHTMLのp要素にid属性とclass属性でそれぞれ定義したCSSのセレクタを指定し、それらに同一のプロパティが宣言されていた場合、カスケーディング（CSSファイルでどちらが前後に記述されているか）に関わらず、id属性(idとclassはidの方がより詳細度が高いため)のプロパティが適用される。

> [詳細度(Specificity)は、どの CSS プロパティが要素に最も関係があるか、すなわち適用されるかをブラウザーが決定する手段です。詳細度は様々な組み合わせの CSS セレクターで構成される一致規則に基づいています。](https://developer.mozilla.org/ja/docs/Web/CSS/Specificity)

#### 詳細度の優先順位

 > 厳密に言うと詳細度を持っていない`

##### 何故詳細度は高くない方が良いのか
 - ルールセットを上書きしようとする際、詳細度が高いとそのルールセットが優先されてしまい、カスケードする（上書きしようとする）ルールセットが上書き出来ないため。但し、ページ内要素によっては、特に単一のものである場合(例えばヘッダーやフッター、グローバルメニュー等)は必ずしも詳細度が低い方が良いとは言い切れない。
 
> [CSSを上書きするケースは非常に多い。そのためメンテナンス性の高いCSSを書くためにもセレクタの詳細度は極力低くし、上書きしやすい状態にしておくのがポイントです。また、詳細度の低いスタイルから先に、詳細度が高いスタイルを後に書くようにするとメンテナンスしやすくなります。](https://yantzn.com/entry/re-css-_study-01/)

### コンポーネント設計と言う考え方

#### そもそもコンポーネントってのは何なのか
直訳すると「部品」、ソフトウェアエンジニアリングでも頻繁に使われる用語なので耳にした事があるかもしれない。厳密に定義するのは（様々な分野で使われるため）中々難しいのだが、前提として「関心の分離」が挙げられる。イメージとして、プラモデルの部品を思い浮かべると良いかと思う。プラモデルの部品は、基本的に設計図で指定されたパーツとしか組み合わせる事が出来ない。他のパーツと接続しようとすると繋ぐジョイントのサイズや位置が違ったりして、組み立てる事が出来ない様になっている。

オブジェクト指向プログラミング経験者であれば、クラスの設計等が正にコンポーネントに当たる(内在するプロパティにprivate宣言をする事により外部から一切触る事が出来ないとか、getterを定義し、クラス内のプロパティを外部から参照する事だけを可能とする等、正に「関心の分離」で言える？)

但し、CSSに置いてスコープ(あるルールセットが利用出来る範囲)は存在しない。そのため、ルールセットの組み立て方と、セレクタの命名規則によって**疑似的に**コンポーネントを組み立てる、と言う手法を取る。下記に...



### [OOCSS]()
オブジェクト指向プログラミングの概念を取り入れた手法。但し、当然CSSにはクラス、カプセル化、スコープと言った概念は存在しないので、あくまでその考え方を用いて実現すると言ったもの。後述するSMACSSやBEM等のベースになる手法。

#### OOCSSにおけるオブジェクトとは
再利用可能なレイアウト、デザインをパターン化し、クラスとして定義したもの、と言って良い。

### [SMACSS]()
CSSを4種類、ないしは5種類にカテゴライズした上で、それぞれのルールや考え方に従って記述する手法。

- Base
  - 各要素のデフォルトスタイル。いわゆる[reset.css]()や[normalize.css]()等もこれに含まれる。
- Layout
  - ヘッダーやフッター、グローバルメニュー、メインコンテンツ等々、ページの構成要素の大枠。クラス名にはl-やlayout-を接頭辞として用いるのが慣習となっているが、上述した様なページ内で単一である事が確定しているものに対してはidや要素セレクタを用いる。但しそれらを使う事によって詳細度が上がるため、メンテナンス性が下がるというデメリットは理解しておく必要がある。
- Module
  - Layoutパターンを除く(内包するとも言える)、ページを構成する要素ほぼ全ての再利用可能なパーツ。見出し、リンク等。SMACSSではこれに対して、特に接頭辞を定めていないが、クラス名にm-やmod-を用いるケースも確認されている、らしい。
